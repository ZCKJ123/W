# 代码压缩：先能压、再压得住

这一轮处理 DSH 时期提过、一直没落地的三条诉求里的第一条半：
**代码压缩**已经落地并跑通对拍；**合并一起跑**和**快速库**接着做。

## 一、已经做出来的东西

`工具\压缩源码.py`：纯文本层的压缩器，只改写法，不改语义。

```
python 工具/压缩源码.py 源.wen 目标.wen [--内联] [--扁平]
```

| 开关 | 做什么 |
|---|---|
| 默认 | 删整行注释、删空行、去行尾空白 |
| `--内联` | 同一缩进层、连续、都是完整简单语句的行，用 `;` 并成一行（上限 6 条） |
| `--扁平` | `如果 A 则 / 如果 B 则 / … / 结束 / 结束` 折叠成 `如果 A 且 B 则`（短路语义不变） |

`工具\压缩对拍.py`：把每个用例压缩一遍，再和原文件比对 stdout + stderr + 退出码。
路径差异会先抹平成 `<FILE>`，避免"只是换了输出目录"被误判成失败。

## 二、实测数字

### 解析时间（`wen.exe --检查`）

`库\自举库.wen`，61,460 字节 / 1,432 行：

| | 字节 | 行 | 检查耗时 |
|---|---:|---:|---:|
| 原始 | 61,460 | 1,432 | 209.6 ms |
| 压缩（内联+扁平） | 56,110（省 8.7%） | 888 | **110.9 ms（省 47%）** |

⚠️ **上面这组数字后来被推翻了，别再引用。** `--检查` 的真实耗时远低于此：
`库\自举库.wen`（61,460B）实测 **18.7 ms**（词法 14.2、语法 2.6、collect+静态 0.3、
名字检查 0.2）。209.6 ms 里混着 PowerShell `Measure-Command` 的进程开销，
对照的还是一个过时构建。

压缩真正省的是**字节**和**行数**，但解析开销几乎不跟这两样挂钩——归因实验见第七节。

### 语义对拍

`测试\用例` 189 个：

| 结果 | 数量 |
|---|---:|
| 完全一致（stdout/stderr/退出码） | **185** |
| 超时跳过 | 1 |
| 只差报错行号/回显源码行 | **3** |

剩下 3 个（`48管理员破坏`、`83安全自检`、`90管理员授权`）是权限错误用例：
错误信息、退出码都一样，只是压缩把语句并到同一行后，报错行号从第 3/4 行变成第 2 行，
`     3 | 申请管理员("wen-test")` 这种源码回显也跟着变了。**这是压缩的固有代价，不是语义损坏。**
要保留原始行号就别加 `--内联`（只删注释和空白，行号不动）。

## 三、四个踩到的坑（都写进工具里了）

1. **括号跨行**：`打印 最大(\n 1,\n 2\n)` 是合法的，按行并会把 `1,; 2` 拼进去 → 语法错误。
   现在先给每行算「行首/行末括号深度」，深度不为 0 的行一律不参与合并。
2. **三引号多行文本**：`将 诗 变成 """…"""` 里面的内容不是代码。
   扫描器要跨行跟踪字符串状态，处在字符串里的行不合并、括号和分号一律不计。
3. **`依赖 X库` 行不能接东西**：压缩器曾把 `依赖 内存库, 数学库; 开启内存压缩(); …` 并成一行，
   库声明被污染。现在 `依赖`、`导出` 都进"绝不参与内联"的名单。
4. **`# 牵引: 全部` 是语义注释**：`Interpreter::scanPull`（wen.cpp 4263 行）会逐行扫 `#` 开头、
   以「牵引」打头的注释，据此配置内存库的压缩牵引。删了它，内存压缩行为直接变（对拍里 28/29/30
   三个用例当场翻车）。现在这类注释原样保留。
   顺带一个更狠的：注释行一旦被并进别的语句，`#` 会把后面整行代码注释掉——
   所以注释行永远独占一行。

## 四、合并一起跑：超指令融合（已落地）

不再一条一条走 dispatch：编译期把常见的指令序列写成一条指令，运行时一次 dispatch 干完。

### 做法

`struct Instr` 加了 `c`/`d` 两个字段（`{op, a, b, c, d}`），指令枚举尾部追加融合指令：

| 新指令 | 字段 | 顶替的原始序列 |
|---|---|---|
| `BC_ADDGK` / `BC_SUBGK` | a=目标槽、b=常数下标、c=SymId | `BC_GN 槽 → BC_K 常数 → BC_ADD/SUB → BC_STG 槽` |
| `BC_ADDGG` / `BC_SUBGG` | a=目标槽、b=源槽、c=目标SymId、d=源SymId | `BC_GN 槽 → BC_GN 槽 → BC_ADD/SUB → BC_STG 槽` |
| `BC_NOP` | — | 被吞掉的原始指令原地改成它 |

关键设计：**不删指令**。被融合的三条原地写成 `BC_NOP`，所以所有跳转目标下标一格不动，
不用重算任何 label、不用建重定位表，风险最小。

融合点只有一处：`WenAsm::stmt` 的 `Assign` 分支。编译完右侧表达式后回头看最后 3 条指令，
形状对得上就改写，然后**不再发 `BC_STG`**（写回由融合指令自己完成）。

数字快路径直接拿 `globals->fastPtr(槽)->num` 算，不构造 `Value`；不是数字就走原来的
`loadInto`（含零参自动调用）→ `applyBinary`（含文本拼接），非数字结果再 `scope->set` 留一份名字表，
与 `BC_STG` 逐字对齐。

### 两个坑（都踩过）

1. **`pc` 多跳一格**。融合后这一处只剩 3 个指令槽（1 条融合 + 2 条 NOP），第 4 条 `BC_STG`
   根本没发射。写成 `pc += 4` 就会吞掉下一条指令——`02分支循环` 的 `打印 合计` 从 15 变成 1 就是这么来的。
   正确值是 `pc += 3`。
2. **旧 `wen.exe` 是过时的构建，字节码路径本身有 bug**。融合版跑全量时出现 14 个不一致
   （100体对拍、119卷积与滤波、122自定义公式 等），一度被当成融合引入的语义偏差。
   拿改动前的源码（`输出\备份\wen.cpp.bak`）重新编译一个基线出来才看清：
   - 基线 vs 融合版：**189/189 完全一致**；
   - 基线 vs 发布的 `wen.exe`：**14 个不一致**；
   - 发布版自己的 `--无字节码` 输出与基线一致，但字节码路径输出不同。
   结论：差异早在融合之前就有，是发布的 exe 落后于源码。用新构建替换后，
   这 14 个用例反而都恢复正常（`100体对拍` 的「总和一致 假」变「真」，`119` 不再报核长错误）。

### 实测

| 场景 | 基线 | 融合版 |
|---|---:|---:|
| 1M 次 `当` 循环（自增 + 累加），`--不快` | 85.6 ms | **81.1 ms（省 5.3%）** |
| 同一脚本默认路径 | 12.1 ms | 12.0 ms |
| 性能门禁：算术 / 函数 / 库调用 | — | 0.12 / 0.13 / 0.99 µs 每语句，全达标 |
| 光追 | — | 265 帧（门槛 165）⚠️ 见下 |

⚠️ 光追那一行的 265 帧复现不出来了：同一份 exe 单独调起来是 226~249 帧，
放进门禁里连续跑完前面几个基准再测就只剩 123~137 帧——这台笔记本几分钟就降频。
所以门禁现在只把光追当**参考项**（照旧打印帧数，不参与退出码），硬门禁是计算类与庞大类。
横向比较要看同一条件下的新旧对照（`工具\基准对比.py` 取 7 轮最小值），
实测新旧两版在 640×360 光追基准上都是 100 ms 左右，没有退化。

为什么只有 5%：顶层简单循环已经被「算术级数」一类专门快路径接管，`--不快` 也关不掉它，
真正落到 VM 的只剩一部分。融合本身是省 3 次 dispatch，收益被快路径稀释了。

### 验证口径（三条一起跑，缺一不可）

```
python 工具\双引擎对拍.py 基线.exe 新.exe     # 跨版本：189 用例
python 工具\VM与AST对拍.py 新.exe              # 自证：字节码 vs --无字节码，189 用例
测试\对拍快路径.ps1 -Cases 2000                # 随机快路径
```

第二条是这一轮新加的：跨版本对拍只能说明两个 exe 一样，**同一个 exe 的 VM 与 AST 路径
是否一致**才能证明编译器/VM 没走歪。这次的 14 个差异就是靠它定位到「发布版过时」而不是「融合有错」。


## 五、还没做的：快速库

把库编译一次、结果缓存成二进制（`.快`），下次加载跳过词法与语法：

- 缓存键 = 源码内容 + 压缩后的字节数 + 语言签名，内容变了自动失效；
- 命中直接把指令流灌进 VM，不重建 AST；
- 先只对 `库\` 下的库文件生效，主脚本仍旧现编。

## 六、验收口径

- 压缩：`python 工具\压缩对拍.py`，必须 185+ 通过，新增失败一律当成语义损坏查。
- 合并：`双引擎对拍.py`（跨版本）+ `VM与AST对拍.py`（自证）都要全通，再跑
  `测试\对拍快路径.ps1 -Cases 2000` 与 `工具\性能门禁.ps1`。
- 快速库：命中缓存的库与现编的库，同一脚本输出必须逐字相同；缓存过期要能自动失效
  （拿旧缓存 + 改过的库源码跑一次，必须走重新编译而不是报错）。
- 解析提速：`python 工具\大源规模测试.py` 看 `--检查` 总耗时与 `[解析计时]` 分项，
  2.6MB 源应当在 0.5 s 内、17.5MB 源应当在 2 s 内；换机器只比同机器的前后值。

## 七、词法提速（快速库的替代落点）

### 先做归因，别急着优化

两个实验把"解析慢在哪"定了下来：

| 实验 | 结果 |
|---|---|
| 3000 行，一行 1 / 2 / 3 条语句（3000 / 6000 / 9000 语句） | 59.2 / 106.9 / 152.5 ms，**每语句约 17 µs，几乎恒定** |
| 语句数固定 6000，行数 6000 / 1000 / 300 | 85 / 105 / 99 ms，**行数基本无影响** |

结论：解析开销跟**语句数**走，不跟行数、也不跟字节数走。所以压缩器"省 47%"那套说法
是测量误差叠出来的假象，压缩的价值在存盘体积和肉眼可读性，不在解析速度。

真正的大头是词法：2.6MB 源里词法 600 ms、语法 75 ms，**词法占 77%**；
17.5MB 源里词法 3,592 ms、语法 529 ms，词法占 87%。

### 瓶颈在哪

每个 token 的起点都要顺序试四种前缀匹配：`tryUnicodeMath`（21 条）、`tryFullWidth`（20 条）、
`isMultiByteDelimiter`（49 条）、`scanOperator`（3+13 条），合计约 85 次字符串比较。
而每次 `startsWith(src_, pos_, "字面量")` 传 `const char*` 都会**隐式构造一个临时 std::string**；
`std::isalpha` / `std::isalnum` 还对着 UTF-8 的每个字节各调一次。

### 落地的六项

| # | 改动 | 省掉什么 |
|---|---|---|
| 1 | `template<size_t N> startsWith(s, pos, const char (&)[N])` | 字面量调用不再构造临时 `std::string` |
| 2 | `startsLit(s, pos, lit, n)` + `PrefixLit{lit,n}` + `buildPrefixTable()` | 每次匹配不再 `strlen`，长度在静态初始化时算好 |
| 3 | `isSymHeadByte(c)`：多字节符号首字节只有 `0xC2/0xC3/0xE2/0xE3/0xEF` | 汉字首字节是 `0xE4~0xE9`，正好在外——中文标识符一次就跳过约 90 次比较 |
| 4 | 两张全角/符号表改成带长度的 `std::vector<Map>`，循环内 `src_[pos_]==m.lit[0] && compare(...)` | 先比首字节，绝大多数直接失败；`pos_ += 6 / 3` 写死长度 |
| 5 | `scanOperator` 先 `switch` 首字符白名单 | 名字、数字进来立刻 `return false`，省掉 17 次前缀匹配 |
| 6 | `isIdentStart/isIdentCont` 改成直接区间比较 | 去掉每字节一次 `std::isalpha/isalnum` |

### 实测（`--检查`，同一台机器）

| 源 | 原始 | 门控+长度预存 | 再加 switch+直接比较 |
|---|---:|---:|---:|
| 2.6 MB / 30,003 行 | 779 ms（词法 600） | 550.6 ms（词法 209） | **463.4 ms（词法 184）** |
| 17.5 MB / 200,003 行 | 4,478 ms（词法 3,592） | 3,190 ms（词法 1,565） | **1,809 ms（词法 806）** |

词法从 0.23 µs/字节 降到 **0.046 µs/字节**（17.5MB：3,592 → 806，4.5 倍），
整条 `--检查` 提速 2.5 倍。语义零副作用：`双引擎对拍 189/189`、`VM与AST对拍 189/189` 全一致。

### 探针

设 `WEN_PROFILE=1` 后 `--检查` 会多打两行（平时零开销）：

```
[解析计时] 词法 x ｜ 语法 x ｜ collect+静态 x ｜ 名字检查 x ｜ 合计 x ms
[检查计时] 读文件 x ｜ 归一+保存块 x ｜ 解析 x ｜ 分行 x ｜ 合计 x ms
```

### 两个坑

1. **`--检查` 不走 `Interpreter::parseSource`，走的是 `parseDiagnostic`。**
   只给前者插计时，跑 `--检查` 一行输出都看不到。两边都得插。
2. **`vpCloudBody` 里的 `fbm3` 报"未声明"**：那个 lambda 定义在
   `if ((!haveDen || builtVar3 != variant) && variant != 27) { … }` 块里，
   而型27 的平面渲染分支整段不执行那个块，自然看不见它。跨分支共用的 lambda
   要提到函数顶层，别留在"只在某型下才执行"的块里。

### 还没动的

- 语法层 138~597 ms（每语句约 5 µs），大头是 AST 节点的 `shared_ptr` 分配与字符串拷贝；
- 固定开销 20 ms（进程启动 16 + `Interpreter` 构造 4）。
  用户要的"启动 30 ms → 10 ms 以内"还差 10 ms 左右，那 16 ms 是 MSVC/MinGW 静态链接
  CRT 初始化的固有成本，能动的只有 `Interpreter` 那 4 ms 里的内置名字表。

## 八、一行一起走：批执行（已落地）

第三项诉求最后一句是"依赖的库写好之后，相关代码其实可以在一行里面并行地走"。
单线程 VM 里没有真并行，能落地的等价物是**同一行的多条赋值走一次 dispatch**：
不改变执行顺序、不改变任何语义，只是把 N 次指令派发合成 1 次。

### 做法

- 新指令 `BC_BATCH`：`a`=批表下标、`b`=这一段占用的指令条数、`c`=批内条数。
- 批表 `std::vector<Batch>` 挂在 `WenAsm` 与 `FuncCallable` 上，字段是
  `kinds`（每条形 0=设常数 1=加常数 2=减常数）、`slots`（目标全局快槽）、
  `ks`（`kconst` 下标，常数本体不复制）、`syms`（非数字回退用的名字）。
- **不删指令**：段的第 1 条原地改成 `BC_BATCH`，段内其余指令改成 `BC_NOP` 留在原处，
  运行时用 `pc += in.b` 整段跳过。所以所有跳转目标下标一个都不动——
  和第四节超指令融合是同一套"绝不改动下标"的约束。
- 编译侧在 `WenAsm::block()` 里把连续 `Assign` 语句交给 `packBatch()`：先试编到
  `code`，逐组认形态，认不出来就 `code.resize(start)` 整段回滚、退回逐条编译。
  形态混着出现也能打成一包（每条的 kind 单独记）。
- 运行时遇到槽里不是数字，回退路径与 `BC_ADDGK` 的 case 逐字同语义
  （`loadInto` → `applyBinary` → `scope->set`），所以文本 `+` 拼接仍然照旧。
- 数字快路径直接改 `fastPtr` 指向的 `Value::num`，不再构造 200 字节的 `Value`。

### 实测（同一台机器，7 轮取最小）

| 基准 | 旧 `wen.exe` | 批执行版 | 变化 |
|---|---:|---:|---:|
| 每轮 4 条同形自增，200 万轮（`--不快` 纯 VM） | 461.4 ms | **140.1 ms** | **3.3 倍** |
| 同样 200 万轮，默认模式 | 47.5 ms | 48.3 ms | 持平（默认模式本来就走别的快路径） |
| 混形（自增/加常数/设常数 各一条）`--不快` | 146.1 ms | 139.2 ms | -5% |
| 函数内三次局部自增（形参 + 两个 `局部`）`--不快` | 257.1 ms | 257.4 ms | 无收益，见下 |
| 性能门禁 算术/函数/库调用 | 0.24 / 0.28 / 2.00 µs | **0.13 / 0.16 / 1.26 µs** | 全线更快 |
| 性能门禁 阶乘 / 圆周率 | 0.20 s / 0.15 s | **0.15 s / 0.10 s** | 更快 |

结论：收益集中在"纯 VM 逐条派发"的路径上，命中时是 3 倍级别；
默认模式里那些已经被专门快路径接管的场景不会退化，也不会再快。

### 验证口径

批执行改动的是指令流本身，所以**必须三条一起跑**，少一条都不算数：

1. `python 工具\双引擎对拍.py <旧.exe> <新.exe>` → 189/189；
2. `python 工具\VM与AST对拍.py <exe>` → 189/189（批执行不能只跟字节码自洽，
   要和 AST 那条路对齐）；
3. `& $PSHOME\pwsh.exe -NoProfile -File 测试\对拍快路径.ps1 -Cases 2000` → 通过。

本次三条全绿（189/189、189/189、2000 组 + 大次数边界），性能门禁 `exit=0`。

### 函数里也能批，但不快

函数体内的连续赋值（形参、`局部` 变量）现在也打包，形态是
`[BC_LINE, BC_LN, BC_K, ADD/SUB, BC_STLL]`（对应顶层那两种的"当前帧"版本）。
但实测**没有收益**：200 万轮三次局部自增 `--不快` 257.1 → 257.4 ms，是噪声。

原因不在 dispatch，而在每次落值都要走 `Scope::set(SymId, Value)`
（`idVars` 哈希或 `svars` 线性扫描）。批执行省掉的那两次 dispatch，在这个开销
面前可以忽略。要提速得先给局部变量做**编译期定槽**，那是另一条线，不在这批改动里。
（这条线已经补上了，见第九节。）

### 还没做的

- 只有赋值能批。`打印`、调用、`如果`、`当` 这类语句一律不参与——它们要么有顺序敏感
  的副作用，要么自带跳转，进批会把语义和下标一起弄乱；
- 依赖检测是"保守地整段放弃"，不是真正的数据流分析。要放进更复杂的语句形态，
  得先有一份"这条语句读了哪些槽、写了哪些槽"的静态信息；
- 函数体内是否走批，取决于局部存取能不能先变快。现在连着批了也白批。（第九节已解决）

## 九、局部数字快槽：让"函数里也能一行一起走"真的快起来

### 上一节留下的那个数

200 万轮三次局部自增 `--不快` 257.1 → 257.4 ms。批已经打上了，指令数确实少了，
时间没动。瓶颈被定位到 `Scope::set(SymId, Value)`：每次赋值都要在 `svars` 里线性
扫一遍 SymId，然后把 200 字节的 `Value` 整体搬过去。批执行省掉的那两次 dispatch
在这个量面前等于零。

### 做法：编译期定槽，数字只碰 8 字节

`Value` 有 200 字节，但循环里的局部变量九成时间就是个数字。所以给函数帧加一排
"数字快槽"，编译期就把形参和 `局部` 变量的槽号排好，运行时数字读写只碰 8 字节。

- `Scope` 新增三个成员：`lnum`（数字值）、`lnumDef`（这个槽里的数字是否有效）、
  `lorder`（槽号 → 变量名，个数是位数，线性扫比哈希表省分配）。
- **唯一真相约定**：`lnumDef[k]` 为真时，只有 `lnum[k]` 算数，`svars` 里那一份是
  过期的、不许读。任何写 `svars` 的老路径（`set` / `assign` / `assignOnce`、exec、
  闭包、未编译语句）写完之后必须清掉对应的 def。`lookup` 的两个重载都先查快槽，
  命中就直接返回数字，不再往下走。
- 两条新指令：`BC_LNQ`（读运算位置，`a`=槽号 `b`=SymId，槽里没数字就退回按名字读）、
  `BC_STLN`（写当前帧，`a`=槽号 `b`=SymId，数字只进快槽，非数字退回 `set`）。
- 编译器侧只在 `compileBody` **整段编译**时打开 `useLocalSlots`：形参先占 `0..n-1`，
  和运行时帧里 `svars` 的前 n 项一一对应，`Function::callSpan` 建帧后把
  `localOrder` 灌进 `lorder/lnum/lnumDef`。运行时临时编块的地方
  （`compileBlock` / `compileForRange`）**不能开**——那些块用的帧是函数对象那边定
  的，这里再排一遍槽号会跟运行时对不上。
- 批执行补了 kind 6/7/8：`[LINE, K, STLN]` 设常数到槽、`[LINE, LNQ, K, ADD/SUB,
  STLN]` 加到槽。落到槽就是 `lnum[k] ±= 常数`，一次 8 字节写。

### 坑一：批只打了 1 段，收益 2%

第一次改完测出来只有 2%。探针显示"批段=1"，而函数体里应该有两段。真相是
`将 甲 变成 甲 + 1` 里 `甲` 的 `declareLocal` 是假（`局部` 声明只在第一次那行），
也不是形参，于是落回 `BC_STLL`，形态对不上新的识别规则，整段回滚。

修法：判定条件从 `(declareLocal || isParam)` 扩成
`(declareLocal || isParam || localSlotIfAny(sym) >= 0)`——前面排过槽的局部变量，
后续赋值继续用同一个槽。改完批段变 2，kinds 是 `8 7 7`。

### 坑二：顶层默认模式退化 22%

收紧之后顶层 `基准_批.wen` 反而从 56.4 涨到 49.5 ms 之前那版是 52。原因是
`lnumClr` 被放在 `set` 开头**无条件**调用，顶层帧没有快槽也要走一趟 vector 检查，
800 万次累计约 9 ms。改成 `if (smallMode)` 才查（只有函数帧是 `smallMode`），
退化消失。

### 还没做的

- 只有"函数体整段编译"才开槽。运行时临时编块（`compileBlock` / `compileForRange`）

- 走 `exec` 的未编译语句看不到快槽（只能读对、不能快）。
