# 作用域检查：函数里的赋值会不会改到全局

## 语言规则（语言规范 36–38 行）

```text
1. 函数参数是局部变量
2. 函数体第一次赋值的名字是局部变量
3. 全局变量可被函数读取；函数内对「已存在的全局名」赋值，改的是全局
```

第 2 条和第 3 条会打架：只要顶层已经有同名变量，函数里的第一次赋值就落到全局，
不会新建局部。实测：

```wen
将 计数 变成 100
函数 加一 则
    将 计数 变成 计数 + 1
    返回 计数
结束
打印 加一()   # 101
打印 计数     # 101 —— 全局被函数改了
```

写库时最容易踩：函数内部的临时变量（`序`、`长`、`果` 这种）如果和某个全局同名，
就会静默改掉全局，症状还往往出现在别处，非常难查。

## 这是不是 bug

不是。这条规则是**承重的**：

```text
自举库   编译语法树 往 当前函数表 / 当前调用补丁 / 主程序模式 里写状态
自举求值  调用值 往 求值环境 里写，求块 往 求值错误 里写
自举运行时 输出文本 往 输出句柄 / 输出开始 里写
```

全仓库扫描出来 27 处，全部是这种「故意改全局」的用法。把默认改成局部作用域
会直接打断自举编译器和求值器，所以不能动语义。

## 能做的：静态检查

`工具/作用域检查.ps1`：扫描一个目录下的 `.wen`，找出
「函数体里赋值的名字在顶层也有同名变量」的位置。

```powershell
powershell -File 工具\作用域检查.ps1          # 默认查 库/
powershell -File 工具\作用域检查.ps1 -Path 你的目录
```

输出：

```text
共 27 处：函数里赋值的名字在顶层也有同名变量，会改到全局。

文件            处数  明细
自举库.wen       16   编译语法树/当前函数表，编译语法树/当前调用补丁，…
自举求值.wen      7   调用值/求值环境，求块/求值错误值，…
自举运行时.wen    4   输出文本/输出句柄，输出文本/输出开始，…
```

判定方式是看原始行首（本语言用缩进对齐块，函数定义和函数结束都在第 0 列），
所以不会把函数内部的局部变量误判成全局。

## 建议写法

```text
库里的临时变量一律加前缀或长名字（块序、切起、切止），别用 序/长/果/值 这种
真的需要改全局时，函数名里写清楚（如 重置编译状态），并在函数上方写一行注释
跑完 作用域检查 再提交，27 处之外的任何新增都值得看一眼
```

## 复现

```powershell
powershell -File 工具\作用域检查.ps1 -Path C:\Temp\scope_test
```


## 现在有语言级解法：`局部`

检查器只能报告，想彻底避免，用新加的关键字：

```wen
将 计数 变成 100
函数 加一 则
    局部 计数 变成 0     # 强制建当前函数帧的变量，不改全局
    将 计数 变成 计数 + 1
    返回 计数
结束
打印 加一()   # 1
打印 计数     # 100 —— 全局没被动
```

```text
只支持解释执行；导出到 C++/JS 等其他目标会报“「局部」声明暂不支持编译到其他目标”
检查器仍保留：老代码里已经存在的隐式全局写入，靠它扫出来
```
